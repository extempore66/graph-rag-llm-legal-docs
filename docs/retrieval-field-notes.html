First, the only object in this document

a chunk

Every number on this page counts chunks. Nothing else.

At ingestion each PDF was cut into pieces of roughly 400 words. One piece is one chunk, and it is one row in the database:

chunk_id     gov.uscourts.nysd.447706.1335.7_1_168
source_file  gov.uscourts.nysd.447706.1335.7_1.pdf
page_start   325
text         "MS. BORJA: Mary Borja for Defendant, Alan Dershowitz…"
vector       [1024 floats]

3,338 exist. That is the whole corpus — 179 PDFs, sliced up.

3,338   chunks in the corpus
  100   the embedding search returns      step 0
   50   vector nominates                  step 1
   12   density nominates                 step 2
 ≤ 50   lexical nominates                 step 3
 ≤ 50   graph nominates                   step 4
    8   survive fusion                    step 5   ← k
    8   judge calls, one per chunk        step 6
    1   answer                            step 7

k is how many chunks reach the LLM at the end. It is 8.

0

One embedding search

→ 100 rows

Before any channel runs, the question is embedded once and searched once:

const vector = await embedQuery(question);      // bge-large, 1024 dims
const ranked = await table.search(vector)
  .distanceType("cosine")
  .limit(100)                                   // max(DENSITY_POOL, CHANNEL_POOL)
  .toArray();

That single ranked array of 100 chunks feeds channels 1 and 2. Channels 3 and 4 never look at it.

Worth holding onto, because it is the reason the whole thing behaves as it does: vector and density are not independent voters. They read the same 100 rows.

1

Vector

→ nominates 50
What it asksWhich single chunk is closest in meaning to the question?

What it does

1. Take the top 50 of the 100 rows.
2. That is its nomination list. Done.

Then four of them get pulled out

Before fusion runs at all:

const reserved   = Math.floor(k / 2);           // k = 8, so 4
const guaranteed = vectorIds.slice(0, reserved); // vector's top 4

In plain terms:

  • Vector's top 4 → slots 1, 2, 3, 4. Locked.
  • Vector's other 46, plus everything the other channels find, compete for slots 5, 6, 7, 8.

Why the four are locked

A measured regression, not caution

The first version fused all 8 slots with equal weight. It fixed the obiter question and simultaneously broke "who is Alfredo Rodriguez" — the chunk that answers it is cosine #3 — but the document that chunk came from ranks only #12 by density, so density outvoted the channel that was right.

Equal weighting only works when channels are independent. Vector and density read the same 100 rows, so they are not. Reserving half the slots makes hybrid strictly additive: it can add what the others find, never subtract what plain similarity already had.

It is a weight. It is the one weight with a measurement behind it rather than a guess.

2

Density

→ nominates up to 12
What it asksWhich document has the most chunks in the neighbourhood?

Its 12 chunks come from the same 100 rows / chunks read by vector. So they usually overlap with vector's 50. A chunk in both lists is not added twice — it collects two score terms, which is exactly what pushes it up.

What it does

1. Take all 100 rows.
2. Group them by source_file — which document each chunk came from.
3. Count how many chunks each document has among the 100.
4. Sort documents by that count. Keep the top 4.      ← Math.ceil(k / 2), k = 8
5. From each of those 4, take its 3 best chunks.
                                                       → 4 × 3 = 12

Note that 100 is a reading depth, not an output size. It counts within 100 and nominates 12.

Why

Both channels hand back chunks. They differ only in what evidence they use to pick them:

  • Vector picks a chunk because that chunk is close to the question.
  • Density picks a chunk because the document it came from has many chunks close to the question.

How a document winning turns into a chunk surfacing

Density never hands back a document. The document ranking never leaves step 2 — all it does is decide which chunks get a good density rank.

A document that comes 1st contributes chunks at positions 1, 2, 3. A document that comes 2nd contributes chunks at positions 4, 5, 6.

Density itself does nothing with these positions — it just hands them to fusion. Previewing step 5’s formula on them:

density position  1  →  1/(60+1)  = 0.01639
density position  6  →  1/(60+6)  = 0.01515
vector   rank    21  →  1/(60+21) = 0.01235

So a chunk from a dense document may sit at vector #21 — a weak term on its own — and still arrive with a strong density term beside it. The two terms add, and that sum is what lifts it into slots 5–8.

The case it was built for

The obiter question is answered by an oral-argument transcript: 102 chunks, all moderately relevant, none outstanding.

Rank the documents by their single best chunk’s cosine and this one comes 14th. Rank them by how many of their chunks reached the top 100 and it comes 2nd.

Vector never computes that first ranking — it is shown only to say what plain similarity would have done. What matters is the second: coming 2nd put three of the transcript’s chunks near the front of density’s list, and one of them reached the final 8.

How to read a density rank

The list is a flattened 12, not a list of documents — so the rank number means a position among those 12:

positions  1– 3   →  densest document, its 3 best chunks
positions  4– 6   →  2nd densest document
positions  7– 9   →  3rd densest document
positions 10–12   →  4th densest document

So density#7 means the top chunk of the third-densest document — not "seventh place."

3

Lexical

→ nominates up to 50
What it asksWhich chunks contain these exact words?

These can be genuinely new. Lexical never touches the embedding search. It scans all 3,338 chunks itself, so it can nominate a chunk vector ranked #2,970.

What it does

1. Send the question to qwen3:8b to be widened.   ← see below
2. Concatenate: original question + both widened outputs.
3. Score all 3,338 chunks with BM25 against that blob.
4. Drop everything scoring 0.                    ← usually most of the corpus
5. Sort by score, take the top 50.

Step 4 is why it often nominates fewer than 50. If only six chunks contain any of the rare terms, it nominates six.

How the widening works

One LLM call returns two strings, and both get thrown into the search alongside the original question.

OutputWhat it is
expanded_querythe same question restated in the words a filing would literally use — jargon and Latin replaced, names and dates kept exactly
hypothetical_chunktwo or three sentences written as if excerpted from a real filing that answers the question

Worked, from the prompt's own example — question: "What was the outcome of the sanctions motion?"

expanded_query:
  "motion for sanctions granted denied; Rule 37 sanctions; the motion is
   granted in part and denied in part; award of fees and costs"

hypothetical_chunk:
  "For the foregoing reasons, the motion for sanctions is granted in part
   and denied in part. Defendant shall bear the reasonable costs and
   attorneys' fees incurred in connection with the motion."

"Rule 37", "foregoing", "attorneys' fees" — rare terms actually found in filings. The original question contained none of them.

Where those words come from

Purely the model's training. Qwen has never seen this corpus — not one of the 179 documents. It is not looking anything up. It generates from what it learned about how American court filings are written, and that works because filings are formulaic: "for the foregoing reasons" appears in millions of documents.

When it guesses a term that appears nowhere in these 3,338 chunks, BM25 scores it zero. Costs nothing.

Why inventing a chunk is safe here

Nothing generated is ever shown to you or fed to the answer model. It exists only to produce search terms. A hallucinated detail costs a slightly worse retrieval, never a wrong answer. The same trick anywhere downstream would be dangerous.

Why the channel exists

The case it was built for

The corpus's genuine quoted judicial dicta — "the Court notes that…" — sat at #329 to #2,970 by cosine. Vector would have to look 2,970 deep. Once the query was widened into the literal phrasing a filing uses, they were #1 to #4 of only 6 matches.

IDF is the part that decides how much a word is worth — rarer words score higher, regardless of the query:

idf = log(1 + (N - n + 0.5) / (n + 0.5))     N = 3,338 chunks, n = chunks containing the word

“the” (n ≈ 3,338) scores near 0. “dictum” (n = 6) scores ≈ 6 — roughly 30,000× more per occurrence.

Known gap

The widening is an LLM call and it fails — measured across eight demo questions, four came back unparseable, all of them enumerative. Lexical then silently falls back to searching the raw question.

4

Graph

→ nominates up to 50
What it asksWho is actually named in here?

These can be genuinely new too. Graph never touches the embedding search. It walks the knowledge graph in ArangoDB.

What it does

1. Tokenize the question. Match against all 2,014 entity names.
       "what did Ghislaine Maxwell say"  →  entity "Ghislaine Maxwell"
       No LLM. Just word overlap.

2. If fewer than 2 names matched, try category words instead.
       "courts" → type court → the top 25 court entities by mention count

3. Expand coreference families.
       "Ms. Giuffre" → Virginia Giuffre, V. Roberts, Giuffre, …

4. Traverse je_mentioned_in from those entities to every chunk
   they appear in.                              (capped at 2,000 edges)

5. Rank those chunks:
       first  by how many DISTINCT seed entities are in the chunk
       then   by total mention count

6. Keep the top 200. Hand up the top 50.

What "tokenize" means here

Separating the words. Still plain text. No embedding, no model.

"Detective Joseph Recarey"  →  {joseph, recarey}
"Mr. Recarey"               →  {recarey}

Lowercase it, split on anything that is not a letter or digit, drop ~50 hand-listed non-identifying words — titles, ranks, esq, llc, court, district. That is what lets those two strings match as one person, in milliseconds, with a reason you can read.

What step 5 actually rewards

A chunk containing both Maxwell and Epstein outranks a chunk containing Maxwell five times. Two entities beats one entity mentioned often.

Why

Two things vector structurally cannot do:

  • Conjunctions. "Filings mentioning both Maxwell and Epstein" — embedding that phrase yields one point resembling a blend of the two, not the set containing both. There is no vector for AND.
  • Surface forms. A question saying "Ms. Giuffre" gets you chunks saying "Ms. Giuffre." Coreference expansion turns that single hit into the whole 876-chunk family, including chunks that only ever say "V. Roberts."

When it nominates nothing

If no entity name and no category word matches, it anchors on nothing and nominates zero — the amber fallback banner. The graph contributed nothing and says so, rather than taking credit for what similarity search found.

Measured

That happened on 11 of 35 eval questions, concentrated in aggregation and counting questions — the ones that name no entity at all.

5

Fusion

→ fills slots 5–8

Four ranked lists arrive. The scores each channel computed are thrown away at the door.

ChannelReadsNominates
vectortop 50 of the 100 rows50
densityall 100 rowsup to 12
lexicalall 3,338 chunksup to 50
graphthe knowledge graphup to 50

Discarding the scores is the point. A cosine distance of 0.31, a BM25 score of 14.2 and a count of 6 chunks are three different units. Combining the numbers means inventing multipliers, and no measurement says what they should be. Ranks are already comparable: #3 means #3 in every list.

The rule

d is one chunk — the same object defined at the top of this document. Everything below is per-chunk.

score(d) = Σ  1 / (60 + rank_c(d))
          c ∈ channels d appears in
  • d — one chunk, the object this whole formula scores.
  • c ranges over only the channels that nominated d. A channel that did not nominate it contributes no term at all — not a zero term, simply absent.
  • rank_c(d) is d's 1-based position in that channel's list. It is the same number shown in the tag: density#7 means the denominator is 60 + 7.

The set of ds is the union of the four lists — up to 162 chunks, fewer in practice because they overlap. The other ~3,180 chunks never enter the calculation. No score, not ranked last. Simply absent.

Why 60

Without it the formula is 1/rank: rank 1 scores 1.0, rank 2 scores 0.5. Any channel's top hit would flatten everything below it. Adding 60 squashes the top of the curve nearly flat.

rank1/(60+rank)
10.01639
20.01613
100.01429
500.00909

#1 beats #2 by 1.6%. #1 beats #50 by only 1.8×. So one appearance never dominates, and what actually moves a chunk up is appearing in more than one list. With 50-long lists that is provable:

worst possible two-list showing:  2 × 1/110 = 0.01818
best possible one-list showing:       1/61  = 0.01639

Being last in two channels beats being first in one. That is the entire behaviour the formula is bought for.

The 60 is RRF_K, the published default from Cormack et al. 2009. It was taken, not tuned.

Worked, from a real run

→ 8 chunks

The eight slots as they came back, with their tags:

[1] vector#1  reserved              ← locked, no fusion
[2] vector#2  reserved
[3] vector#3  reserved
[4] vector#4  reserved
[5] vector#16 density#7 lexical#5
[6] vector#11 density#2 lexical#38
[7] vector#14 density#3
[8] vector#19 density#5

Slots 5–8 scored from nothing but those tag numbers:

slot 5   1/(60+16) + 1/(60+7) + 1/(60+5)   = 0.043468
slot 6   1/(60+11) + 1/(60+2) + 1/(60+38)  = 0.040418
slot 7   1/(60+14) + 1/(60+3)              = 0.029387
slot 8   1/(60+19) + 1/(60+5)              = 0.028043

Descending — which reproduces the observed slot order exactly.

And the property in one line: a chunk sitting at vector#5 and nowhere else scores 1/65 = 0.015385. It loses to all four above it, including slot 8, whose best placement is #5 in one channel and #19 in another. Two mediocre placements beat one good one.

Slots 5–8 ranked 11th, 14th, 16th and 19th by plain cosine. A vector-only top-8 would have taken cosine #5 through #8 instead. Hybrid returned four chunks naive would have missed, and dropped four naive would have taken — while keeping naive's best four untouched in slots 1–4.

The one that justifies the whole design

The chunk answering "is there any obiter dicta here" — in a corpus where the word obiter appears zero times in 3,338 chunks — arrived at slot 8 of 8, tagged vector#21 density#3:

1/(60+21) + 1/(60+3) = 0.01235 + 0.01587 = 0.02822

A chunk at vector#6 and nowhere else scores 0.01515. The obiter chunk outscores it by nearly 2× despite being fifteen places worse on similarity. Density carried it. A vector-only top-8 misses it by thirteen places.

Reading the tags in the UI

how to decode a row

Two families of tag sit on every source row, and they come from different stages.

Channel tags — the grey line under the page numbers

Each names a channel and the rank that channel gave this chunk. The number is the same one the formula uses: density#7 means the denominator is 60 + 7.

TagMeaning
vector#Nstep 1 — cosine similarity
density#Nstep 2 — position in the flattened 12
lexical#Nstep 3 — BM25 over the widened query
graph#Nstep 4 — entity traversal
reservedslot 1–4, placed by rule — carries no rank number

Several tags on one row means several channels nominated that chunk independently. Two more lines appear only on chunks the graph reached: reached via <names>, and beneath it the evidence — entity, role, and the literal quote from the edge.

cited — the green badge before the filename

Not a channel. It comes from step 6, and means the sufficiency check marked that chunk relevant.

So the two families answer different questions: channel tags say how this chunk got here; cited says what the sufficiency check made of it once it arrived.

What a missing tag tells you

No graph# anywhere, with the blue anchored panel showing. The traversal ran, anchored, nominated 50 chunks — and lost every slot.

Live run — "Which courts appeared in these filings?"

The traversal linked 25 court entities, reached 1,299 mentions across 1,004 chunks, nominated 50 — and not one of the eight final slots carried a graph# tag. Four were reserved; the other four went to chunks carrying two or three tags each.

Structural, not accidental. Four slots are gone before fusion runs, and RRF rewards chunks nominated by more than one channel — but vector and density read the same 100 rows, so they stack routinely. Graph is independent of both, so it almost never stacks. The reserved slots protect vector from being outvoted. Nothing protects graph.

6

Checking sufficiency

→ sufficient, yes or no
What it asksDoes this one chunk help answer the question?

Note what it does not ask. It never asks "can these eight answer it." It asks eight small questions and counts the answers.

What it does

1. Take the 8 chunks fusion produced.

2. Fire 8 SEPARATE calls to qwen3:8b, in parallel.
       Each call sees exactly ONE chunk.
       Each call sees no other chunk. Ever.

3. Each returns one boolean:
       { "answers_question": true }   or   { "answers_question": false }

4. Count the trues.

5. sufficient = (count > 0)

The schema is the enforcement

That is the entire shape it is allowed to reply in:

const SINGLE_SCHEMA = {
  type: "object",
  properties: { answers_question: { type: "boolean" } },
  required: ["answers_question"],
};

There is no field long enough to hold an answer. An earlier version paired each boolean with a short why string, and the model used that prose field as somewhere to start answering the question. Remove the field and it structurally cannot.

Why one call per chunk

The original checked all eight in a single call and returned a boolean per chunk. That looks independent. It is not.

Measured on "who were the defense attorneys" — answer in slot 1 of 8 
all 8 chunks                → sufficient = false, 0 cited
the same 8, minus slot 7      → sufficient = TRUE
slot 7 swapped for another    → false
k=1 false · k=2 TRUE · k=4 false · k=8 false

Holding the retrieved set fixed, "who were" and "who are" give the same result — the tense only moved the query embedding, which changed three of the eight neighbours. The result for slot 1 was a function of the other seven the whole time.

That cannot be fixed by instructing the model to check independently, because the instruction was already there. So the set stops being a variable: one call, one chunk, no opportunity for the others to interfere.

"Sufficient" is computed, never asked

Nothing asks the model whether the chunks are sufficient. It is arithmetic on the eight booleans:

const sufficient = relevantNumbers.length > 0;

That moved in three stages, and the arc is the point:

VersionHow sufficient was decided
OriginalAsked the model. It returned sufficient: true with zero chunks marked relevant — then named Epstein as a person called Maxwell.
GuardedThe model's answer ANDed with a rule it kept ignoring.
NowNever asks. Counts the trues.

Same lesson as the pinned schema in entity resolution: an instruction the model can ignore becomes a rule it cannot, once it moves out of the prompt and into code.

The threshold is one

One "yes" out of eight and it answers. Eight "no"s are required to refuse.

Where that bites

Asked "what is this corpus about," every retrieved chunk genuinely is a piece of this corpus — so all eight checks truthfully return yes, and it answers from 0.24% of the corpus. Corpus-level questions do not fool the gate. They satisfy it.

A failed or unparseable call also counts as no — failing toward refusing rather than toward answering from unvetted context.

7

Answer, or refuse

→ text on screen

If sufficient is false

The refusal is assembled in JavaScript. No LLM call at all:

answer: `These chunks do not contain the answer -- ${verdict.missing}.`

This is the anti-confabulation move. Having decided the chunks cannot answer, sending them back to a model to write that up is the round trip that produces a confident non-answer. Building the sentence in code makes that round trip unreachable.

If sufficient is true

1. One streaming call to qwen3:8b.
2. It receives ALL EIGHT chunks — not just the relevant ones.
3. Its instruction: "They have already been judged sufficient,
   so answer directly and confidently."

No hedging language, because hedging was step 6's job and step 6 is over. Neither model is ever in a position to talk itself into writing something: step 6 has nowhere to put an answer, and step 7 was never asked whether to give one.

Where the citations come from

The sufficiency check, never the answer. The answer prompt forbids source numbers in the reply. The cited chunks are resolved in code from the eight booleans — result i is about source i, and the real chunk id is reattached positionally.

That is the lesson from an early failure where the model, asked to echo a long dotted identifier, returned ":65839" — a real id with a stray colon picked up from the prompt's own formatting. Small integers derived positionally in code cannot be mangled.

Known gap

Step 7 reads all eight chunks including the seven just marked irrelevant — the results drive the gate and the citations, but do not filter the context.

Known gap

The cited badge means "the sufficiency check marked this chunk relevant," not "this sentence came from here." Usually the same; not guaranteed.

Entity resolution

ingestion

Two candidate channels run in parallel, not in sequence, and neither one decides anything. They only build a shortlist.

new mention
   ├── Channel 1: Jaro-Winkler on the bare name  ─┐
   │                                              ├── union by entity_id, cap 5
   └── Channel 2: embedding of surrounding text ──┘            │
                                                               ▼
                                                     Step 5: LLM judges

Channel 1 — name string only. Case-insensitive Jaro-Winkler against every existing entity of the same type, threshold 0.85, sorted, top 5. Catches J. Smith / John Smith.

Channel 2 — context only, never the name. What gets embedded is a ±15-word window around the mention, not the name and not the whole chunk:

…counsel regarding [Ms. Giuffre] and the scheduling of…
 └──── 15 words ────┘      ↑      └──── 15 words ────┘
                      the mention

That snippet is embedded once and used twice — for the search, and as the stored vector row. It catches Virginia Roberts ↔ Virginia L. Giuffre, where the names share almost nothing but the surrounding language does. It needed a guard: left alone it nominated Ghislaine Maxwell as a candidate for Jeffrey Epstein — no name relation at all, just two names that co-occur constantly.

Where the decision is made

Neither channel. One LLM call, and it gets facts rather than just names: the new mention's name, type and textual evidence; the candidate's name; the role in that specific matched mention; and the docket numbers and dates from that mention's chunk. Decision per candidate: same / different / unsure.

Roles are mostly empty on purpose — 18,576 of 19,009 edges carry role: "none", because extraction sets a role only when the word is spelled out next to the name. Better to under-assign than to guess.

Three structural guards, because prompting failed

  • The schema pins the count. minItems/maxItems built per call to the exact candidate count. Without it, constrained decoding returned 2 decisions for 1 candidate.
  • No entity IDs in the schema at all. Candidates are numbered; the real ID is reattached in code.
  • A deterministic backstop. A same decision that came only from the embedding channel, with neither name generic and Jaro-Winkler below 0.6, is downgraded to unsure. That came from the model merging two unrelated people whose snippets overlapped almost entirely because both sat in one six-person discovery request.

Then: same attaches to the existing entity, no match creates a new one, and every unsure writes a je_possible_duplicates edge — the source of the 413 queued flags.

Two library defaults that cost real damage

Case sensitivity was load-bearing. The library defaults to case-sensitive; SOUTHERN DISTRICT OF NEW YORK vs Southern District of New York scored 0.517. 110 nodes — 5.6% of the graph — were redundant purely on case.

Sorting before the cap was load-bearing. The first run capped an unsorted list, returning an arbitrary 5 above threshold instead of the best 5. On honorific-dense names, 80–130 clear 0.85 for one probe, so the exact 1.000 self-match got crowded out. Result: 38 separate "Mr. Barton" nodes, 9.6% of the graph.

Both failed safely — missed merges, never false ones — and neither showed up in a 200-chunk test, because the effect scales with entity count.

Known gap

Coreference was run with --type person only. Courts, organizations and locations were never resolved — so SDNY exists as three separate nodes (664 + 120 + 86 mentions) with no same_as edges, and its true count is 870, not 664.

Adding documents later

ingestion

"Adding one filing means rebuilding the graph" is too pessimistic. The 19.8 hours built 2,014 entities from nothing — every mention arrived with no graph to compare against, so almost every one triggered an LLM call.

full buildone new filing
new mentions19,009~100
entities to compare againstgrowing from 0fixed at ~2,014
string comparisons—~200,000 (milliseconds)
LLM calls~19,000~60

Minutes, not hours. Three phases with different concurrency rules:

  • Phase A — per document, fully parallel. Chunk, embed, extract, write. No shared state. Key it on a content hash, not a filename — courts re-file corrected versions constantly, and a filename tells you nothing about whether you have seen the bytes.
  • Phase B — entity resolution, serialized per matter. Two workers on two filings would both see no existing "Mr. Recarey" and both create one.
  • Phase C — the retroactive sweep. The genuinely new piece.

Why the sweep is cheap: merges are edges, not rewrites

Suppose the graph already holds V. Roberts and Virginia Giuffre as separate nodes because nothing ever connected them. A new filing says "Virginia Roberts Giuffre, formerly known as Virginia Roberts." Two existing entities should now merge — and nothing in the pipeline looks back.

The architecture never collapses two nodes into one. Identity is a same_as edge, and retrieval expands the family at query time. So a retroactive merge is INSERT one edge — not "find every mention edge pointing at B, rewrite it to A, delete B, hope nothing else referenced it." Three consequences: merging is O(1) whatever the entity's history; it is reversible; and you never rewrite history, which is what lets a bad merge be audited later.

What stays hard

  • Order dependence. Whichever spelling arrives first becomes the display name. Fixable — pick the family's most complete name at query time rather than storing a winner.
  • Non-determinism. Re-running the same documents in a different order gives a slightly different graph. Uncomfortable for a system producing legal evidence.
  • Merge cascades. Merging A and B can make the family match C. Do one pass and flag the rest — cascading merges are how one node swallows the graph.

A new matter, or a new corpus

Harder in a way that is not about compute. Two matters both have a "John Smith," and they are not the same person. Entity resolution must be scoped to the matter and must never look across the boundary — that is an ethical-wall requirement, not just correctness.

Between the two tenancy models, database per matter is the default worth taking: isolation is a legal requirement, and legal requirements should not rely on every future query remembering to include a filter. Deleting a matter at engagement end becomes dropDatabase, which is itself a retention requirement. Cross-matter entities — the expert witness who appears in thirty matters — go in a separate, small, curated registry, where the link is a human decision and never an automatic merge.

Thresholds should become per-corpus configuration rather than global environment variables. Depositions and product documentation want different chunk separators, entity types, and similarity thresholds. For a new corpus, calibrate: ingest a sample, run candidate generation at several thresholds, have a human label 100 pairs, record the chosen threshold with the corpus.

The trap worth remembering

A sample predicts cost. It does not predict correctness. The "Mr. Barton" bug could not appear in a 200-chunk test — it only triggers when enough names clear the threshold to crowd out the true match, and at 220 entities not enough did. Onboarding needs a full-run audit: sort entities by name similarity and eyeball the top few hundred clusters. An afternoon of work, and the step that catches the class of bug that only exists at scale.

Corpus-level questions

the gap

Asked live, on the shipping two-phase path: "Give me an overview of the documents in this case. What is this corpus about?" It did not refuse. It answered confidently in 54 seconds:

"The corpus involves legal proceedings related to Jeffrey Epstein and Ghislaine Maxwell… The case includes a complaint against Epstein and Maxwell, referencing individuals such as Sarah Kellen, Lesley Groff…"

The corpus is Giuffre v. Maxwell, 15-cv-07433 — a defamation suit. "15-cv-07433" appears 147 times in the chunks and "defamation" 324 times. The answer names neither, and describes the wrong kind of case with the wrong parties. Not a refusal and not an answer: a plausible paragraph that gets the shape of the case wrong.

Why

It saw 0.24% of the corpus. Eight chunks from 5 of 179 documents, three of them from the same exhibit compilation. The graph channel abstained outright — no name to anchor on.

And the abstention machinery is what let it through. The sufficiency check asks, per chunk, does this bear on the question? For "what is this corpus about," every retrieved chunk genuinely is a document in the corpus. Eight independent, individually-truthful yes results sum to sufficient: true. Corpus-level questions do not fool the gate. They satisfy it.

The deeper reason, which channel independence does not touch

Every channel is a top-k selector: vector 50 of 3,338, density 12, lexical 50, graph 50. Union at most ~160 chunks, ~5% of the corpus — then fusion cuts it to 8. More independent channels give a broader pool to pick 8 from. They do not give a view of 3,338.

The architecture is a selection problem; an overview is an aggregation problem. Those do not converge however good the selection gets. RETRIEVAL_TOP_K = 8 is a constant, and no branch anywhere says "this question is about the whole corpus, do something different."

The system already computes the right answer and discards it

On "which courts appeared in these filings," the Graph Path panel lists 25 court entities with mention counts across the whole corpus, while the prose names two. The panel is the better answer to the question. The traversal answered it corpus-wide in ~50 ms; the answer path then discarded that and read eight pages.

The panel is an aggregation. The prose is a selection. The same distinction, visible in one screenshot.

Known gap

Four of the 25 listed "courts" are not courts — Court, SPECIAL MASTER, Your Honor and a judge's name slip past the generic-name filter.

What closing it would take

the gap

ArangoDB's Importer builds hierarchical communities and has an LLM write a report per community. enable_community_embeddings defaults to true while chunk and edge embeddings default to false — that ordering is their statement about which surface is primary. Global Search map-reduces over those reports, and their docs say it suits "questions that require an understanding of the dataset as a whole."

The build is the smaller half

ANSWER_NUM_CTX is 8,192 and the largest document is 106,681 tokens — 13× the window. So "summarize each of 179 documents" is not one call per document:

StageCalls
L1 — chunk-groups → partial document summaries388
L2 — roll up the 65 multi-group documents65
L3 — batch 179 summaries → 8 batches → 1 root9
Total462 ≈ 4.4 hours

The half that makes it work

A static summary tree answers exactly one question: "what is this corpus about." Ask "which courts appear" and the root has nothing to say, because whoever wrote it did not know you would ask.

Global Search's map-reduce runs at query time, not build time. Every report is handed the user's question and returns a partial answer plus a relevance score; the zeros are dropped and the survivors reduced into the final answer. The root summary is barely used. The generality comes from asking all 179 units the specific question — which is also why their own docs call it resource-intensive. On this hardware: ~179 map calls × ~4s ≈ 12 minutes per question, serialized.

Units, and the demo-able version

Documents are the free partition — source_file already exists, it is deterministic, and citations stay honest. But the graph is there to do it properly: Leiden over 2,014 entities and 19,009 edges is seconds, and communities cut across documents, which matters when a thread runs through a dozen filings and has no home document.

The version that fits the latency budget: build the summaries offline, embed them, then at query time vector-search the summaries, take the top ~15, and map-reduce over only those — about 60 seconds. Not true Global Search, since top-k returns. But top-15 over 179 summaries that each cover a whole filing is a far better bet than top-8 over 3,338 chunks.

What it would cost

Citations degrade from "page 47, these words" to "filing 1335.4" — trading the strongest differentiator for coverage. An 8B model summarizing OCR-noisy legal exhibits is unmeasured risk. And it goes stale: a new filing invalidates its summary and every roll-up above it.

Where the artifacts live

the gap

A summary is text. The embedding is a derived index over it.

The shape already exists in je_chunks: a text column for what the LLM reads, a vector column for how you find it. Nobody says a chunk is an embedding. A summary is the same.

An embedding is one-way. 1024 floats, and no function turns them back into words. So an embedding can never be an answer — only a lookup key. In the lifecycle, the vector's job ends the moment the search returns IDs; from there the text of the winners goes to the model. The 4.4 hours buys 179 pieces of English prose; the embeddings are seconds of bge-large at the end and are regenerable from the text at any time. The text is not regenerable from anything except another 4.4 hours.

Nothing here is temporary

A summary that takes 4.4 hours and is deterministic given the corpus is an artifact, the same way je_entities is. The pipeline already made this call once: je_raw_extractions still holds all 3,338 rows even though entities were built from them, because it was expensive and you need it to debug.

The existing split is clean and worth following — LanceDB owns text and vectors; ArangoDB owns identity, structure and edges, with a few scalar fields duplicated into Lance so .where() filtering needs no round trip.

  • ArangoDB je_summaries — deterministic _key, level, scope, the chunk IDs it was built from, model and timestamp.
  • ArangoDB je_summarizes — an edge collection carrying the hierarchy, so "give me the leaves under this batch summary" is one AQL query.
  • LanceDB je_summaries — a new table, not je_chunks.
The warning that matters most

Do not append summaries into the existing je_chunks Lance table. Every existing vector search would start returning summaries as if they were chunks — the naive retriever, the vector and density channels, the graph reranker all change behaviour silently, and every row in runs.jsonl is invalidated.

Keep the 388 L1 partials too. A 4.4-hour job gets interrupted, and when a document summary is wrong you need to know which partial poisoned it. They cost ~250 KB.

For resumability, improve on the existing flag pattern: the unit of work is a chunk group, which has no home row, so make the key deterministic and let existence be the flag. Idempotent by construction — no flag to fall out of sync, and re-running after an interrupt costs one existence check per unit instead of an LLM call.

Field worth adding

built_from_chunk_ids (or a hash) on every summary, so staleness after a new filing can be detected rather than assumed — otherwise the only safe move is rebuilding all 462.
